# PRD — Clinician Chart Navigation Story Stress Test

## Status
Approved planning artifact for downstream execution. No code implemented by this workflow.

## Context
Current pi-chart UI surface is a static cockpit prototype generated by `scripts/agent-canvas.ts` into `docs/prototypes/pi-chart-agent-canvas.html`. It currently emphasizes the Overview state: patient banner, left nav, vitals strip, problem timeline, right clinical worklist, floating editable artifact pane, and bottom Pi-agent dock.

This PRD defines a clinician-first user story to stress-test whether the UI supports real shift-start clinical work across the whole chart, not just the Overview panel.

## User Story
As a bedside nurse coming onto day shift for Patient 002, I need to use pi-chart as my clinical cockpit to review handoff, prior vitals, medications, notes, labs, radiology, and due work, then ask Pi-agent to organize my shift, so I can start care with a clear prioritized plan while preserving the distinction between chart truth, draft workspaces, and co-pilot chat.

## Primary Actor
- Bedside RN coming onto shift.
- Synthetic clinician: `rn_shane` or equivalent.
- Patient: Patient 002, CAP day 1, respiratory watcher.

## Product Positioning Rules
- Pi-chart is the clinical cockpit.
- Pi-agent is a co-pilot.
- Chat is process, not chart truth.
- Right rail is a clinical worklist, not an artifact scratchpad.
- Floating panes are editable draft/charting workspaces.
- Use `Chart`, `Charted`, and `final clinical write`.
- Do not use legacy VCS-style finalization wording; use Chart/Charted/final clinical write instead.

## Clinical Safety Rules
- Synthetic fixture data only.
- Agent must not auto-chart medication administration.
- MAR items may be blocked, staged, or reviewed.
- Medication administration requires scan/attestation.
- Zosyn due at 12:00 remains blocked pending scan/attestation.

## RALPLAN-DR Summary

### Principles
1. **Chart-first orientation** — urgent patient context must be visible before chat or generated drafts.
2. **Shift-work realism** — flow must reflect actual nurse cognition: handoff → trends → meds → notes → due work → results → shift organization.
3. **Interruptible continuity** — due work can interrupt review without losing the nurse’s place.
4. **Safety boundary clarity** — medication charting remains gated by scan/attestation.
5. **Clinical instrument aesthetics** — dense, sharp, precise UI; no SaaS/pastel/chat-first drift.

### Decision Drivers
1. Can the nurse build a safe patient model within 3–5 minutes?
2. Can the UI support cross-chart review without hiding due clinical work?
3. Can the UI keep chart truth, drafts, and co-pilot advice visually separate?

### Options Considered

#### Option A — Static storyboard states first — chosen
Represent the full shift-start journey as storyboard states in the existing generated cockpit prototype, with clear panels/panes and validation tests.

Pros:
- Fits current architecture.
- Fast to execute.
- Strong for visual/IA stress testing.
- Avoids premature app framework or heavy interaction design.

Cons:
- Does not fully prove interactive navigation state recovery.

#### Option B — Minimal interactive chart shell
Add client-side state transitions for left nav, workspace pane changes, due vitals charting, and Pi-agent prompt response.

Pros:
- Better validates real navigation and interrupted workflow.

Cons:
- Higher complexity inside static generator.
- Risk of coding behavior before storyboard is accepted.

#### Option C — Separate prototype artifact
Create a new standalone journey prototype separate from current cockpit.

Pros:
- Less risk to current Overview prototype.

Cons:
- Splits product truth and weakens regression path.

### Decision
Use Option A for the next execution pass. Design storyboard states inside the existing cockpit generator. Add a light interaction plan only where necessary to make the story inspectable.

## Clinician Journey: Start-of-Shift Clinical Recon

### 0. Launch state: Overview
The nurse opens Patient 002 and lands on Overview.

Visible anchors:
- `π-chart / overview`
- Patient 002 + FULL CODE
- WATCHER / respiratory acuity
- CAP day 1
- SpO₂ 89% on 6L simple mask
- HR 112, RR 30
- lactate 2.8
- open loop due 09:50
- right rail with Due / Overdue, Staged Charting, Generated Drafts, Blocked MAR Items, Charted / Done
- Pi-agent dock collapsed/slim

Stress question:
- Can the nurse understand “this patient is respiratory-watch, due for reassessment, and meds require safety gates” without opening chat?

### 1. Open handoff report
The nurse opens the handoff report from either left nav (`Care plan / handoff`) or right rail (`Staged Charting` / handoff item).

Expected UI:
- Floating editable workspace opens as a handoff report form.
- Source context rail shows linked notes, vitals trend, and current open loops.
- Actions: Discard draft, Stage draft, Chart / FINAL CLINICAL WRITE.
- Patient banner, right worklist, and Pi-agent dock remain visible.

Stress question:
- Can handoff be read and charted without losing urgent watcher context?

### 2. Review previous-shift vital signs
The nurse opens `Vitals / flowsheet`.

Expected UI:
- Center workspace shows previous-shift trend view.
- Include SpO₂, HR, RR, BP, O₂ delivery/device changes, and time windows.
- Current due vitals are visible as either a worklist item or inline due marker.
- Handoff pane can stay open, minimize, or be replaced by a vitals charting workspace.

Stress question:
- Can the nurse see trajectory, not just latest values?

### 3. Review MAR
The nurse opens `Meds / MAR`.

Expected UI:
- Scheduled meds, due meds, prior Charted administrations, held/refused items, and scan-required items are differentiated.
- Zosyn due at 12:00 is present.
- Zosyn is blocked pending scan/attestation.
- Agent may prepare context/reminder but cannot Chart medication administration.

Stress question:
- Is the medication safety boundary impossible to miss?

### 4. Read provider notes
The nurse opens `Notes` / provider notes.

Expected UI:
- Provider assessment and plan are reachable.
- Nursing notes and Pi-agent summaries are visually distinct.
- Generated summaries cite source notes and are not styled as Charted truth unless Charted.

Stress question:
- Can the nurse find the actual provider plan without confusing it with generated synthesis?

### 5. Chart due vital signs during review
While reviewing notes/MAR, vitals become due.

Expected UI:
- Due-vitals item appears or stays prominent in right worklist.
- Nurse opens a vitals charting workspace.
- Form includes timestamp, SpO₂, HR, RR, BP, O₂ device/support, work-of-breathing note, and escalation acknowledgement.
- Final action reads `Chart` and implies `FINAL CLINICAL WRITE`.

Stress question:
- Can routine charting be quick while respiratory escalation criteria remain visible?

### 6. Review labs
The nurse opens `Labs / dx`.

Expected UI:
- ABG/lactate is visible with timestamp and trend relevance.
- Lactate 2.8 is connected to respiratory/CAP problem context.
- Abnormal/relevant labs are prioritized, but normal labs are not hidden in a way that feels unsafe.

Stress question:
- Can the nurse tell which result matters now and why?

### 7. Review radiology reports
The nurse opens radiology/imaging from `Labs / dx`, `Evidence`, or an explicit imaging item if added.

Expected UI:
- CXR/report impression, timestamp, status, and relevance to CAP/respiratory trajectory are visible.
- Imaging can be read alongside current problem timeline or evidence context.

Stress question:
- Does imaging feel like part of chart review, not a disconnected attachment?

### 8. Ask Pi-agent to organize the shift
The nurse opens the Pi-agent dock and asks: “Organize my shift and tell me what I should pay attention to.”

Expected agent response shape:
- Immediate watch items.
- Due tasks by time.
- Medication safety gates.
- Labs/radiology follow-ups.
- Documentation suggestions.
- What would trigger escalation.

Expected UI boundary:
- Response is advisory/process.
- Any generated chartable text becomes a draft artifact or staged charting item.
- Agent does not mutate final chart truth directly.

Stress question:
- Can the co-pilot help organize work without becoming the source of chart truth?

### 9. Return to Overview
The nurse returns to Overview.

Expected UI:
- Updated worklist state is visible.
- Charted vitals move to Charted / Done.
- Blocked MAR remains blocked if scan/attestation has not occurred.
- Open loop and escalation triggers remain visible if unresolved.

Stress question:
- Does the Overview remain the cockpit home base after cross-chart work?

- Live data binding.
- Real medication administration charting.
- Full route framework migration.
- Full conversational AI backend.
- Authentication/user management.
- Replacing pi-chart with a generic dashboard.

## Component/IA Implications

### ProductHeader
Must remain stable across chart navigation. It should not expand into dashboard chrome.

### PatientBanner
Always visible. Must retain patient identity, FULL CODE, respiratory watcher, encounter, and current O₂ support.

### LeftChartNav
Needs a coherent journey path:
- Overview
- Handoff / Care plan
- Vitals / flowsheet
- Meds / MAR
- Notes
- Labs / dx
- Radiology / imaging, either explicit or nested under Labs/Evidence
- Evidence / source chain
- Agent Canvas as process/draft review lane

### MainWorkspace
Should support storyboard states:
- Overview timeline
- Handoff report
- Previous-shift vitals trend
- MAR review
- Provider notes
- Due-vitals charting
- Labs
- Radiology
- Agent shift plan review

### ClinicalWorklist
Must remain cross-cutting and prioritized, not just artifacts:
- Due / Overdue
- Staged Charting
- Generated Drafts
- Blocked MAR Items
- Charted / Done

### FloatingWorkspacePane
Use for editable handoff/vitals/charting/draft forms. Must be resizable and preserve markdown/editor affordances where chart text is being edited.

### PiAgentDock
Slim by default. Expands for the nurse’s shift-organization prompt. Output must be advisory and link to worklist/artifact lanes when chartable content is produced.

## Acceptance Criteria
1. A clinician can follow the entire shift-start journey from visible UI affordances.
2. Overview is default and remains the home base.
3. Handoff report can be opened and read in a workspace.
4. Previous-shift vitals can be reviewed as trends with O₂ device context.
5. MAR clearly differentiates due/reviewed/blocked/Charted items.
6. Zosyn due at 12:00 remains blocked pending scan/attestation.
7. Provider notes are reachable and distinct from generated summaries.
8. Due vitals can be opened as charting work and finalized via Chart / FINAL CLINICAL WRITE.
9. Labs show lactate 2.8 and connect it to the respiratory problem.
10. Radiology/imaging report is reachable and context-linked.
11. Pi-agent can organize the shift without appearing to write chart truth directly.
12. Right rail remains a prioritized clinical worklist.
13. No legacy VCS-style finalization wording appears in user-visible prototype copy.
14. Screens remain readable at 1440x1080 and 1280-wide viewport.

## ADR

### Decision
Create a clinician journey storyboard in the existing pi-chart cockpit prototype before adding heavier interaction behavior.

### Drivers
- Current architecture is static HTML generated by TypeScript.
- User wants UI/UX stress testing and story iteration for a different execution agent.
- The highest risk is IA mismatch, not implementation mechanics.

### Alternatives Considered
- Build interactive shell now: deferred because it may overfit premature interaction behavior.
- Create separate prototype: rejected because it splits product truth from current cockpit.
- Write prose only: rejected because execution needs concrete UI states and acceptance criteria.

### Consequences
- Faster implementation handoff.
- Stronger visual/story coverage.
- Limited validation of real click/state behavior until follow-up.

### Follow-ups
- After storyboard acceptance, add minimal client-side transitions and Playwright navigation checks.
- Consider whether radiology deserves primary nav or nested placement under Labs/Evidence.
