# Foundation decision matrix

Status: rescue review artifact

Purpose: challenge inherited foundations before the rebase hardens them.

| Foundation topic | Option | Benefits | Risks | Rejected because | Evidence needed | Current recommendation |
|---|---|---|---|---|---|---|
| Language | TypeScript-only pi-chart and ledger | Fast iteration; aligns with brownfield chart code and agent tooling. | Harder to guarantee canonicalization/hash determinism across environments; risks mixing UI/projection/kernel concerns. | Not rejected for chart projections, but insufficiently justified for reusable kernel. | Compare determinism, packaging, test ergonomics, adapter cost. | Keep TS viable for pi-chart projections/adapters, not as assumed kernel choice. |
| Language | Rust kernel plus TypeScript chart adapters | Stronger determinism, small kernel boundary, reuse outside pi-chart. | Binding/tooling complexity; slower iteration; FFI/WASM/N-API decision needed. | Not rejected; aligns with `pi-ledger` direction. | Proven K0-K6 interface and integration mechanism decision. | Preferred for `pi-ledger`; adapter mechanism deferred. |
| Language | Rust all the way through pi-chart core | Strong type/determinism story. | Over-rotates chart workflow/projection/docs/UI-adjacent work into lower-ergonomics stack. | Too broad without evidence. | Spike showing chart projections gain enough to justify rewrite. | Defer. |
| Storage | Filesystem/NDJSON/Markdown as fixture/export/current backend | Human-readable, simple, existing test evidence. | Can become accidental production storage; weak concurrency/query story. | Not rejected as fixture/export. | Define import/export vs runtime backend boundary. | Keep as evidence/export/fixture surface only. |
| Storage | Append ledger plus chart read indexes | Separates truth from projections; supports replay and ContextPacket compilation. | Requires index freshness, rebuild, and adapter contracts. | Not rejected. | Kernel K0-K6 evidence; read-index PRD. | Preferred direction after ledger interface proves. |
| Storage | FHIR server/database as internal storage | Mature healthcare API surface. | Forces internal model into external resource shapes; may hide agent-native context semantics. | Too much lock-in for core memory substrate. | Only consider as boundary adapter proof. | Reject as internal core for now; boundary adapter later. |
| Dependencies | Minimal dependencies with explicit canonicalization/schema choices | Easier audit, deterministic behavior, lower supply-chain risk. | More custom code; slower feature breadth. | Not rejected. | Dependency inventory and determinism tests. | Preferred baseline. |
| Dependencies | Adopt healthcare/FHIR/openEHR packages internally | Faster standards coverage. | Standards/model gravity; dependency risk; may not solve ContextPacket needs. | Not justified before adapter ADR. | Package evaluation against boundary-adapter requirements. | Defer to adapter lane. |
| Dependencies | Heavy framework/ORM/service stack now | Faster service scaffolding. | Premature architecture, migration risk, hidden magic for agents. | No current production backend decision. | Service/backend PRD with runtime requirements. | Reject for this phase. |
| Package boundary | `pi-ledger` independent kernel, `pi-chart` adapter consumer | Clean ownership; reusable kernel; protects chart from hash/admission concerns. | Adapter design waits on kernel evidence. | Not rejected. | K0-K6 closeout, consumer contract inventory. | Current accepted boundary. |
| Package boundary | Fold ledger back into `pi-chart` | Faster local integration. | Violates ADR020; couples kernel to chart brownfield/prototype. | Superseded by ADR020. | None unless ADR020 is reversed. | Reject. |
| Package boundary | Split pi-chart into chart-core, chart-adapters, chart-ui now | Cleaner future seams. | Premature decomposition before core primitives close. | Not rejected, but too early. | Rescue closeout and first substrate PRD. | Defer; identify candidate seams only. |
| Fixture strategy | Synthetic kernel fixtures first | Stable deterministic evidence for ledger. | Less clinical richness. | Not rejected. | K0-K6 closeout. | Keep in pi-ledger. |
| Fixture strategy | Curated patient cases as chart scenario pressure | Captures clinical reality and workflow value. | Overfit to patient_002 or prototype scenario. | Not rejected. | Corpus coverage/gap map and HITL signoff. | Use after foundation decisions; evidence only until promoted. |
| Fixture strategy | Migrate current `patients/` into new substrate immediately | Fast realism. | Imports brownfield shape and patient-fixture assumptions into foundation. | Violates clean-canvas posture. | Only after adapter/import PRD. | Reject for foundation phase. |
| Standards posture | FHIR/openEHR as boundary adapters and reference constraints | Reuse external rails without internal capture. | Requires mapping work later. | Not rejected. | Adapter PRD, external export/import goals. | Preferred. |
| Standards posture | FHIR/openEHR as internal canonical model | Familiar clinical structures. | Model mismatch for claim ledger, context packet, omission accounting, agent receipts. | Premature and constraining. | Strong interoperability-first ADR. | Reject for now. |
| Standards posture | Ignore standards until product works | Maximum freedom. | Reinvents worse EHR rails and loses interoperability discipline. | User explicitly wants leverage, not reinvention. | None. | Reject. |
