# Golden-vector and conformance design

Date: 2026-05-31
Ultragoal story: `G004-golden-vector-and-conformance-design`
Status: planning artifact; vectors are specified, not generated.

## Purpose

Define a transport-agnostic conformance suite for the private clinical-truth service contract. The suite must prove that any transport or client binding preserves `ledger-core` semantics for canonical bytes, Record hash, append admission, revision target proof, bitemporal point reads, and fail-closed error behavior.

## Design principles

1. **Rust kernel is cryptographic authority.** Expected canonical bytes and hashes are generated by `ledger-core`, never by `pi-chart` TypeScript.
2. **Transport agnostic.** The same vector fixture must run through in-process service harness, gRPC/UDS, and any later transport without changing expected semantics.
3. **Positive and negative vectors are equally authoritative.** Rejections are part of the contract.
4. **Patient-scoped isolation is explicit.** Every vector names target patient ledger and Claim subject patient.
5. **Store-owned metadata is expected-output only.** Requests never include `accepted_at`, `seq`, `batch_id`, Record hash, Entry hash, previous link, or head.
6. **Registry version is part of the vector.** Predicate policy changes produce a new vector-suite version.

## Fixture layout proposal

```text
pi-ledger/conformance/clinical-truth/v1alpha1/
  manifest.json
  registry/
    predicate-registry.v1.json
    predicate-registry.v1.sha256
  vectors/
    001-base-observation-append/
      request.json
      expected.validate.json
      expected.append.json
      expected.canonical.json
      expected.point-read.json
    002-revision-target-proof/
      seed-ledger.json
      request.json
      expected.append-revision.json
    1xx-negative-*/
      request.json
      expected.error.json
```

Consumer mirrors under `.scratch/` or `pi-chart` may reference these vectors, but `pi-ledger` owns canonical expected cryptographic outputs.

## Manifest fields

- `suite_id`: e.g. `clinical_truth.v1alpha1.registry-v1.kernel-k12`
- `contract_version`: `clinical_truth.v1alpha1`
- `registry_version`
- `registry_hash`
- `canonicalization_id`
- `kernel_commit_or_build`
- `vectors[]`: id, purpose, operation(s), request path, expected paths, required error code if negative

## Required positive vectors

| Vector | Operations | Purpose | Must assert |
| --- | --- | --- | --- |
| `001-base-observation-append` | `ValidateClaim`, `PreviewAppendAdmission`, `AppendClaim`, `GetEntry`, `PointRead` | Happy-path base observation such as an EF or vital observation with source/evidence payload. | canonical bytes, Record hash, assigned seq/accepted_at shape, Entry hash/head, point-read visibility. |
| `002-context-segment-observation` | validate/admit/append | Decision D001: `context_segment` is `shape=observation`, predicate `observation.context_segment`. | Shape and predicate accepted only when registry declares observation. |
| `003-review-attestation-act` | append base act | Decisions D003-D005: review/attestation as separate `act` fact with evidence target. | Target linkage carried as `evidence: EvidenceRef[]`; target not mutated. |
| `004-revision-target-proof` | seed base append, `AppendRevisionClaim`, point-read | Correction appends only with target id + current Record hash. | Prior entry remains; revision entry accepted; point-read known-time behavior changes by accepted history. |
| `005-two-concurrent-appends` | two `AppendClaim` requests against same patient | Service-side append order. | Unique seq/head chain; deterministic ordering rule or observable serialized order. |
| `006-snapshot-rebuild-roundtrip` | append several entries, `SnapshotLedger`, `ValidateLedgerSnapshot` | Storage/rebuild conformance. | Rebuilt head equals original; entry and record hashes recompute. |
| `007-cross-patient-isolation` | append same Claim id in two patient ledgers where subject matches each ledger | Patient ledger isolation. | Separate sequences/heads; no cross-ledger target proof. |
| `008-point-read-bitemporal` | append base + correction at distinct known times | Valid-time/known-time query. | Known-before-correction sees base; known-after-correction sees correction semantics per query policy. |

## Expected output schema for canonical/hash vectors

Each positive vector with cryptographic output records:

```json
{
  "canonicalization_id": "<kernel id>",
  "input_claim_path": "request.json#/claim_json",
  "canonical_utf8_hex": "<hex-encoded canonical bytes>",
  "record_hash": "sha256:<64 lowercase hex>",
  "accepted_entry": {
    "seq": 1,
    "accepted_at": "YYYY-MM-DDTHH:MM:SSZ",
    "batch_id": "<service assigned>",
    "entry_hash": "sha256:<64 lowercase hex>",
    "previous_entry_hash": null,
    "head_hash": "sha256:<64 lowercase hex>"
  }
}
```

The suite may use deterministic service clocks for vector generation, but production callers still cannot supply accepted metadata.

## Expected output schema for errors

```json
{
  "contract_version": "clinical_truth.v1alpha1",
  "operation": "AppendClaim",
  "error": {
    "code": "PATIENT_MISMATCH",
    "field_path": "claim_json.subject.patientId",
    "retryable": false,
    "kernel_error": "<optional kernel error id>"
  }
}
```

Error messages may vary; `code`, `field_path` where applicable, and `retryable` are conformance fields.

## Generation workflow

1. Build a deterministic in-process harness around `ledger-core` safe paths.
2. Load the production candidate registry fixture and compute its content hash.
3. For each positive vector, run the safe service operation chain and write expected canonical/hash/entry/query outputs.
4. For each negative vector, run the operation and record the normalized contract error code.
5. Run the same vectors through gRPC/UDS transport; compare semantic responses after removing transport envelope noise.
6. Publish vector manifest and expected outputs as versioned test fixtures.

## Client conformance expectations

`pi-chart` adapter tests should consume the vectors as black-box contract evidence:

- It may assert service-returned Record hashes, but must not recompute them in TypeScript.
- It may use vector requests to build fixture round-trip tests.
- It must preserve evidence/source/review payloads through request construction.
- It must handle negative errors as review/retry prompts where appropriate, never by silently mutating chart truth.
